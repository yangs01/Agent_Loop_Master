# Q8 详解 · 一个 case 逐帧看破法 1/2/3

> 配套阅读：`学习问题记录.md` 的 Q7（三条破法总纲）、Q8（时间线概述）。
>
> 这一篇是 Q8 的**逐帧细化版**。同一个任务，同一条 token 时间线，但每一帧都摊开六件事：
>
> 1. 用户这一轮的指令是什么（原话）
> 2. 这一轮读进上下文的是什么
> 3. 哪些被压缩了
> 4. 哪些被保留了
> 5. 哪些被写到了窗口之外（外部存储）
> 6. 哪一步派了子 agent、子 agent 拿到什么上下文、又带回什么
>
> 看的时候盯住一个东西：**主上下文窗口里到底躺着什么。** 每一帧我都给它拍一张快照。

---

## 0. 先把舞台摆好

**项目**：一个开源博客系统（Node.js + Express + SQLite），评论功能是"平铺一层"的——谁都只能评论文章，不能回复别人的评论。

**总目标**：重构评论系统，**支持嵌套回复（楼中楼）**，并且**不能改坏现有测试**。

**窗口预算**：200k token（下文所有百分比都是相对这个数）。

**关键角色**：
- **主 agent**：全程在循环里干活的那个"你"，它的上下文窗口就是我们要盯的舞台。
- **子 agent**：主 agent 需要时克隆出去的"分身"，进独立小黑屋干脏活，只带一句结论回来（见 Q4）。
- **外部存储**：`CLAUDE.md`、`TODO`、`session memory`、迁移文件、代码文件——统统在**窗口之外**的磁盘上。

一个贯穿全篇的记账原则（这也是追问①的答案，先立在这里）：

> **有两条完全独立的账。**
> - **任务账**：写代码、写迁移脚本、跑测试、决定下一步——**每一轮都在调 LLM**，这是干活本身。
> - **压缩账**：为了给窗口腾地方而做的管理动作——**T1/T2 不额外调 LLM，T3/T4 才调**。
>
> 后面凡说"不调模型 / 代价为 0"，指的都是**压缩账**，绝不是说任务停了模型。

## 帧 1 · 第 0～30%：上游隔离 + T1 微压缩

### ① 用户指令（第 1 轮，原话）

> "帮我把这个博客的评论系统重构一下，支持嵌套回复（能回复评论、楼中楼），注意别把现在的测试改挂了。"

这句话是**整个任务的宪法**。记住它——它会被"逐字保留"到最后一次全量压缩里，一个字都不许丢。

### ② 这一轮读进上下文的是什么

几乎**没有原始代码**进主上下文。因为主 agent 意识到"搞清楚评论系统现在长啥样"是一件脏活：要 grep 一堆关键词（`comment`、`reply`、`Comment`、`parent`……）、要翻近 20 个文件、要看 14 个测试用例的细节。

如果这些原始内容全进主窗口，光勘探就能吃掉 30%＋ 的预算，而且大多是"看过就没用"的噪声。

所以主 agent 的选择是：**不自己翻，派个分身去翻。**

### ⑥ 子 agent：进去什么、出来什么

| | 内容 |
|---|---|
| **主 agent 交给子 agent 的上下文** | 一句任务指令："勘探这个仓库的评论系统实现。定位：评论的数据模型、增删查改逻辑在哪些文件；数据库有没有表示层级关系的字段；现有测试覆盖了哪些评论相关用例。**只返回结论，不要把文件内容贴回来。**"（外加系统提示 + 工具定义，靠缓存前缀共享） |
| **子 agent 小黑屋里干的脏活** | grep 十几个关键词、`Read` 了 ~20 个文件、逐个看了 14 个测试用例——**这些原始内容全部只存在于子 agent 自己的窗口里** |
| **子 agent 带回主上下文的结论** | 一段浓缩结论：<br>· 逻辑集中在 `CommentService.js` 和 `models/Comment.js`<br>· `comments` 表字段：`id / post_id / author / body / created_at`，**没有 `parent_id`**（这就是要加的）<br>· 相关测试 14 个，在 `test/comment.test.js`，覆盖"发评论/删评论/按文章拉评论列表"<br>· API 入口在 `routes/comments.js` |
| **子 agent 用完** | **销毁**。它窗口里那 20 个文件的原始内容随之蒸发，从没进过主上下文 |

> 这就是**破法一的上游**（Q7 结尾那条）：*最好的压缩，是一开始就别让垃圾进来。* 20 个文件的原始 token 从源头就被挡在主窗口外。

### ③④ 压缩了什么 / 保留了什么

这一段主 agent 每轮做 **T1 微压缩（MicroCompact）**：

- **压缩掉**：上一轮工具调用里冗长、重复、已经用过的输出（比如某次 `ls` 的完整目录树、某个已读文件的尾部）。
- **保留住**：缓存前缀（系统提示 + 工具定义那段不动，保证缓存命中不失效）、当前有效的结论。
- **代价**：**0，不调模型**（只是数组里清理/重排旧工具结果）。

### ⑤ 外部存储

暂无写入。任务刚起步，还没有"阶段成果"值得落盘。

### 📸 帧 1 结束 · 主窗口快照（占用 ~30%）

```
[系统提示 + 工具定义]      ← 常驻，缓存前缀
[用户第1轮指令 · 逐字]     ← 宪法，绝不动
[子agent带回的勘探结论]    ← 一段话，不是20个文件
[最近几轮的思考/工具结果]  ← T1 持续清理中
```

窗口很干净。**注意：20 个文件、14 个测试的原始内容一个字都不在这里。**

## 帧 2 · 第 30～60%：开始动手 + T2 归档

### ① 用户指令

这一段用户基本没插话（偶尔一句"嗯，继续"）。主 agent 在**自主循环**里干活。

### ② 读进上下文的是什么（按需拉取）

现在真要动代码了，主 agent 才**按需**把具体文件拉进来（这正是第 4 篇"按需检索"）：

- `Read` 了 `models/Comment.js` 的真实内容（这次是主 agent 自己读，因为要改它）。
- `Read` 了 `CommentService.js` 里拉评论列表的那个函数。
- 写了一版数据库迁移脚本（加 `parent_id` 字段）。

> **⚠️ 追问① 在这里现形**：写迁移脚本 = **任务账**，当然是 LLM 干的、当然调模型。别和"压缩不调模型"混为一谈。

### 干活流水（会产生大量历史）

1. 写迁移脚本 v1 → 跑 → 失败（外键约束写错）。
2. 改迁移脚本 v2 → 跑 → 过。
3. 改 `Comment` 模型加 `parent_id`。
4. 写了**第一版**"拉评论树"的代码 → 自测发现思路不对（想用递归 JS 循环查库，太慢）→ **推翻重写**。

到这里历史已经变长：帧 1 的勘探结论、被推翻的迁移脚本 v1、被推翻的第一版树代码……都还堆在窗口里。占用逼近 60%。

### ③ 压缩了什么 —— T2 归档（Snip）

触发 **T2 归档**：把**最老、已经没用**的消息异步挪到归档区。具体挪走：

- 帧 1 那段勘探过程的中间碎片（结论留着，过程碎片归档）。
- 迁移脚本 v1（已被 v2 取代，留 v2 就够）。
- 第一版被推翻的树代码。

### ④ 保留了什么

- 用户第 1 轮指令（逐字，永远留）。
- 迁移脚本 v2（现行版本）。
- `parent_id` 已加好这个**事实**。
- 最近几轮的有效上下文。

### T2 的代价（对齐追问①）

> **归档这个动作本身不调 LLM、代价为 0** ——它只是把消息对象从"活动窗口数组"搬到"归档数组"，是内存搬家，不需要再问一次模型"帮我把这段总结一下"。
>
> 这跟"迁移脚本是模型写的"完全不冲突：**写脚本走任务账（调模型），归档走压缩账（不调模型）。**

### ⑤ 外部存储

主 agent 顺手把迁移这件事记进了 `CLAUDE.md` 的进度区（可选，但好习惯）：`- [x] DB: comments 表已加 parent_id（迁移 20260712_add_parent_id.js 已过）`。

### 📸 帧 2 结束 · 主窗口快照（压缩后回落，占用 ~45%）

```
[系统提示 + 工具定义]
[用户第1轮指令 · 逐字]
[勘探结论（精简）]
[迁移脚本 v2 + "parent_id 已加"的事实]
[最近几轮工具结果]
───────── 归档区（不占窗口）─────────
[勘探过程碎片、迁移v1、被推翻的树代码v1]
```

## 帧 3 · 第 60～75%：分级预警 + 缩短输出 + T3 折叠

### ① 用户指令（第 2、3 轮，穿插）

- 第 2 轮："回复列表现在能出来了吗？我看嵌套好像没生效。"
- 第 3 轮："对，就是楼中楼渲染不出来，你查一下。"

于是进入 **debug 拉锯**。

### ② 读进上下文的是什么

主 agent 重写了"拉评论树"的查询，改用 SQL 递归查。然后开始来回 debug 七八轮：

- 试 A：普通 JOIN → 只出一层 → 失败日志进窗口。
- 试 B：应用层递归查库 → N+1 查询、慢 → 失败。
- 试 C：递归 CTE（`WITH RECURSIVE`）→ 语法错 → 失败。
- 试 D：修正递归 CTE → **通过**。

每一次"跑测试 / 跑脚本"都吐回一大坨输出（堆栈、SQL 日志、查询计划……）。历史飞速膨胀，占用过 60%，逼近 75%。

### ③ 压缩了什么 —— 分级预警逐级升级

**过 60%：主动缩短工具输出。** 那些失败尝试的完整堆栈，只保留**失败的那一行关键信息**，其余截断。（比如一坨 40 行的 SQL 错误日志，压成 "CTE 语法错：near 'RECURSIVE'"。）

**过 75%：升级 T3 分段折叠（Collapse）。** 把"试 A 失败、试 B 失败、试 C 失败、试 D 通过"这一整段曲折 debug，**分段摘要**成一句：

> "拉评论树：应用层递归导致 N+1（慢）→ 改用递归 CTE，修正语法后测试通过。"

- **T3 的代价**：**少量 LLM 调用**（这是压缩账里第一次真的调模型——因为要"读懂那段曲折再写成一句"，纯搬家做不到）。

### ④ 保留了什么

- 用户第 1、2、3 轮指令（逐字）。
- "递归 CTE 方案已通过"这个**结论**（曲折过程被折叠，结论留下）。
- 最近一次成功的测试结果。

> 这就是**破法一的精髓**（Q7）：*压不压、压多狠不写死，随压力梯度自动升级。* 60% 轻轻削、75% 才动模型折叠——永远先用最便宜的手段。

### ⑤ 外部存储

暂缓（下一帧集中写）。

### 📸 帧 3 结束 · 主窗口快照（占用被 T3 压回 ~65%，但还在涨）

```
[系统提示 + 工具定义]
[用户第1/2/3轮指令 · 逐字]
[勘探结论 + 迁移事实]
[debug 折叠成一句："N+1 → 递归 CTE → 通过"]  ← 原本七八轮曲折
[最近一次成功测试结果]
```

## 帧 4 · 第 75%：破法三的关键动作——写笔记（外部存储）

### ① 用户指令（第 4 轮 · 极其重要）

> "对了，嵌套别无限套，**最多 5 层**，太深了页面没法看。"

**这句话是一个关键决策输入**，等下你会看到它被特别对待。

### ⑤ 外部存储 —— 这一帧的主角

debug 告一段落，主 agent 主动把**阶段成果写进窗口之外的持久存储**。这不是压缩，是**主动落盘**（破法三）：

写入 `CLAUDE.md` / `TODO` / `session memory`：

```
## 评论系统重构 · 进度
### 已完成
- [x] DB: comments 表加 parent_id（迁移已过）
- [x] 拉评论树：递归 CTE 实现，测试通过
### 待办
- [ ] 前端渲染嵌套评论（楼中楼 UI）
- [ ] 补测试：嵌套回复的用例
### 关键决策
- 最大嵌套深度 = 5 层（用户第4轮明确要求）
- 递归查询方案：WITH RECURSIVE（放弃应用层递归，因 N+1）
```

### 这一帧的题眼

> 写完这一刻，**关键事实同时活在两个地方**：
> - 活在**对话历史**里（窗口内，随时可能被之后的压缩动到）。
> - 活在**磁盘**上（`CLAUDE.md`，压缩碰不到它）。
>
> 这份"双份保险"就是等下能救命的东西。

### ② 读进上下文

写笔记本身是**任务账**（主 agent 调 LLM 生成这段笔记内容并写文件），但它写完并不需要一直把全文留在窗口——文件在磁盘上，要用再读。

### 📸 帧 4 结束 · 快照（占用 ~78%，且外部有了一份笔记）

```
主窗口：[系统提示][用户1/2/3/4轮指令][结论若干][近期消息]
磁盘（窗口之外）：
  CLAUDE.md ← 进度/待办/关键决策（含"最大5层"）
  迁移文件、代码文件、session memory
```

## 帧 5 · 第 90%：破法二——T4 全量压缩守保真度

### 为什么到这里

前端渲染又写了一大段，继续跑测试、看报错，占用一路涨到 **90%**。T1/T2/T3 这些轻手段已经削不动了（能归档的早归档了，能折叠的早折叠了）。触发**最后的重锤 T4 全量压缩**。

### ⑥ 子 agent 再次登场（这次是"压缩子 agent"）

T4 不是主 agent 自己压，而是 **fork 一个子 agent** 专门做摘要：

| | 内容 |
|---|---|
| **子 agent 拿到的上下文** | 主 agent 当前**整段历史** + 一份 **9 段结构化模板**（`BASE_COMPACT_PROMPT`）。**关键**：它和父 agent 共享同一套系统提示与缓存前缀——是**缓存命中，不是重新付一遍前缀的钱** |
| **子 agent 在草稿纸上做什么** | 先在一个 `scratchpad` 块里，按时间顺序把整段对话捋一遍，边捋边想"哪些必须留、哪些能扔"——这是**思考过程** |
| **子 agent 正式产出** | 按 9 段模板写出的**结构化摘要** |
| **草稿纸的命运** | 注入回主上下文前，**scratchpad 被丢弃**——思考改善了摘要质量，却**不占用刚腾出来的预算** |

### ③ 压缩了什么（T4 砸掉的）

窗口里**中间那一大段陈旧历史**：前端渲染的多轮试错、大量已被折叠过又累积的工具结果、早期各种中间态……从几万 token 被砸成几百 token 的摘要。

### ④ 保留了什么 —— 9 段模板强制不许丢

这是防失忆的核心。摘要**必须**含这 9 段：

| # | 段 | 本例里具体是什么 |
|---|---|---|
| 1 | 原始需求与意图 | "重构评论系统支持嵌套回复，不改坏现有测试" |
| 2 | 关键技术概念 | 递归 CTE、`parent_id`、最大嵌套 5 层 |
| 3 | 相关文件与代码片段 | `models/Comment.js`、`CommentService.js`、`routes/comments.js`、迁移文件、`test/comment.test.js` |
| 4 | 遇到的报错与修复 | N+1 → 递归 CTE；CTE 语法错 → 修正后过 |
| 5 | 解决问题的思路 | 放弃应用层递归，用 SQL 递归查 |
| 6 | **所有用户消息（逐字）** | 第1轮宪法 + 第2/3轮 debug 诉求 + **第4轮"最多5层"** |
| 7 | 待办任务 | 前端渲染楼中楼、补嵌套用例测试 |
| 8 | 当前进行中 | 前端渲染 UI |
| 9 | 下一步 | 渲染折叠/展开、跑全量测试 |

> **第 6 条是命门**：用户四轮原话逐字保留，直接堵死第 4 篇担心的"用户原始意图被压没了"。哪怕摘要别的地方压狠了，**用户说过的话一个字不少**。

### ⑤ 外部存储

不变——`CLAUDE.md` 那份笔记**完全没被 T4 碰到**，它压根不在窗口里。（这一点马上救命。）

### 📸 帧 5 结束 · 快照（90% → ~35%，断崖式下跌）

```
[系统提示 + 工具定义]          ← 地板：常驻
[9段结构化摘要]                ← 中间几万token被砸成这一段
[用户1/2/3/4轮指令 · 逐字]     ← 摘要第6段保住
[最近1~2轮原始消息]            ← 最新指令/最后测试结果，不压
```

**这就是追问②的答案实体**：占用从 90% 一下掉到 ~35%。掉不到 0，是因为上面那几行是"地板"（系统提示 + 摘要本身 + 近期消息 + 可能读回的笔记，都得占 token）。

## 帧 6 · 崩溃时刻：破法三兜底，两难被拆掉

### 假设最坏情况

假设 T4 的摘要**还是漏了**一条细节："前端渲染要处理**折叠/展开状态**"。（摘要再结构化，也总有漏的可能——这正是第 4 篇说的"压狠会失忆"。）

### 没有破法三 = 灾难

压缩一结束，主 agent 接着干前端，可能就**忘了做折叠/展开**，交付一个残缺的 UI，用户回来骂人。这就是"保真度 vs 预算"死结的杀伤力。

### 有破法三 = 有惊无险

但真实流程里，**压缩一结束，主 agent 第一件事是读自己写的笔记**（`CLAUDE.md` / `session memory`）：

```
读回 CLAUDE.md →
  待办里明明白白写着：前端渲染楼中楼、补测试
  关键决策写着：最大 5 层
  （即便"折叠/展开"当初也记进了笔记，这里就直接读回）
```

细节回来了——**因为它从来不只活在对话里，它躺在磁盘上。**

### 甚至更省：`sessionMemoryCompact`

还有个实验性优化：既然后台一直在维护 `session memory`，那 T4 那一刻**干脆直接拿 session memory 当摘要用**，连"fork 子 agent 做一次摘要"的那次 LLM 调用都省了。

## 帧 7 · 收尾：锯齿波继续

主 agent 拿着完整信息把前端渲染做完（含折叠/展开、限制 5 层）、补上嵌套用例测试、跑全量测试通过。

期间占用又从 ~40% 涨回高位 → T1/T2/T3 继续削峰 → 逼近 90% 再来一次 T4 → 再砸回 ~35%……如此**锯齿波（sawtooth）**循环，直到任务完成。

> T1/T2/T3 一路"削峰"，尽量**推迟甚至避免**下一次昂贵的 T4。**T4 是最后的重锤，不是常规手段。**

### ⚠️ 关键澄清：下降不是只发生在 90%

一张常见的简化图，会画成"只有 90% 才断崖下跌"：

```
（简化示意 · 只画了 T4 大断崖）
90% ┤        /|          /|
40% ┤       / └─►       / └─►     ← 每次 T4 = 断崖下跌
35% ┤      /     \     /     \
    └────────────────────────► 时间
        ↑T4压缩点   ↑又涨到90%再压
```

但这只是为了突出重点而**抹掉了小台阶**。真相是：**60%、75% 也会降，只是降幅小、不显眼。** 原因在于四层压缩腾出的 token 量天差地别：

| 层级 | 触发点 | 对曲线的效果 | 降幅 |
|---|---|---|---|
| **T1 微压缩** | 每一轮 | 主要**压平上升斜率**（垃圾刚进来就清掉，几乎即时抵消） | 几乎看不出降，更像"涨得慢一点" |
| **T2 归档** | 逼近阈值 | 一个**小台阶**下跌 | 小 |
| **T3 折叠** | ~75% | 一个**中等台阶**下跌 | 中 |
| **T4 全量** | ~90% | **断崖** | 大 |

所以真实曲线是**一条带小锯齿的上升沿 + 90% 处的大断崖**：

```
（真实示意 · 上升沿本身就带小缺口）
token 占用
90% ┤              _/|                    _/|
    │            _/  |                  _/  |     ← 大断崖 = T4
75% ┤          _/┘   |    ← T3小台阶  _/┘   |
    │        _/      |              _/      |
60% ┤      _/┘       |   ← T2小台阶_/┘      |
40% ┤    _/          └─►          _/        └─►
35% ┤  _/             \         _/           \
    └───────────────────────────────────────► 时间
       ↑上升沿是"毛边斜线"：T1让它涨得慢，T2/T3途中削几刀
```

一个诚实的补充——四层里效果并不齐:

- **T2/T3 是"真下降"**：把已经堆在窗口里的旧历史搬走/折叠，占用数字确实往下掉一截。
- **T1 更像"减速"**：它在垃圾刚进来时就清掉，所以你看到的不是"降"，而是"斜率变缓、迟迟涨不上去"。

这正是破法一的设计意图（呼应帧 3）：**用 T1/T2/T3 一路"削峰"，尽量推迟甚至避免那记昂贵的 T4。** 90% 的断崖之所以少见，恰恰是因为前面三层一直在悄悄放血。

## 三个追问的最终定论

### 追问①：不调 LLM 怎么写迁移脚本？——两条账，别混

- **写迁移脚本**走**任务账**：当然调 LLM，每一轮干活都在调。
- **"T1/T2 不调模型"** 说的是**压缩账**：归档、微压缩这些"给窗口腾地方"的管理动作，是内存搬家/清理，不需要**额外**再问一次模型。
- 所以"到这里还没为压缩动模型"的准确含义是：**没为了压缩而额外调 LLM**，不是整个系统停了 LLM。

### 追问②：全量压缩后 90% 会掉吗？——会，断崖式掉，且这就是它的全部意义

- 90% → ~35%，**一次性砸下一大截**，你说的"变成 50%"方向完全对，通常还能更狠。
- **掉不到 0** 是因为有"地板"：系统提示+工具定义、那份 9 段摘要本身、最近 1~2 轮原始消息、可能刚读回的笔记——这些都得占 token。
- 压完继续涨、涨了再压 = **锯齿波**，让长任务能一直跑下去不撞上限。

### 追问③：上下文波动只有 90% 才下降吗？——不，60%/75% 也降，只是降幅小

- **不是只有 T4 才让曲线往下**。60% 缩短工具输出、75% 的 T3 折叠、逼近阈值的 T2 归档，都会让占用往下掉一小截。
- 差别在**降幅**：T4 是断崖（几万 token → 几百），T2/T3 是小/中台阶，T1 甚至更像"让上升变慢"而非"下降"。
- 所以真实曲线不是"光滑斜线 + 90% 断崖"，而是**带小锯齿的毛边上升沿 + 90% 大断崖**。那张只画 T4 的图是简化示意（详见帧 7 的澄清）。

### 破法三为什么是"最关键"

> 压缩丢掉的只是**临时对话流水**；关键事实（用户要什么、做了哪些决策、还剩哪些待办）**同时活在窗口之外的磁盘上，随时读回**。
>
> 正因如此，压缩**可以放心压得更狠**——反正丢的不是命根子。"保真度 vs 预算"的死结，就在"关键信息本来就不只活在对话里"这一点上，被彻底拆开。
