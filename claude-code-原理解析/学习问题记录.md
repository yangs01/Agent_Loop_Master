# 《Claude Code 原理解析》学习问题记录

> 这里记录学习过程中产生的疑问与解答，按提问顺序累积。

---

## Q1：DeepAgent（LLM 出 plan + subagent 执行）的 plan，和 Claude Code 的 plan 有啥区别？不都是 LLM 规划的 plan 吗？

**提问背景**：第 2 篇提到 Claude Code「没有独立 planner，规划溶解进循环」，但像 DeepAgent 这类架构，不也是 LLM 先出一个 plan，再让 subagent 去执行吗？既然 plan 都是 LLM 生成的，两者到底差在哪？

### 一句话回答

差别不在「谁生成 plan」（都是 LLM），而在 **plan 生成之后，它是"活的"还是"死的"**——是能随每一步观察不断被推翻重写，还是一次性冻结下来指挥后续执行。

### 关键区分：Plan-as-Data vs Plan-as-Behavior

这是理解两者差异的核心。你被"都是 LLM 出的 plan"这句话迷惑了，因为它只描述了**生成的瞬间**，没描述**生成之后 plan 扮演什么角色**。

| 维度 | DeepAgent / Plan-and-Execute 类 | Claude Code |
|------|-------------------------------|-------------|
| plan 的形态 | 一份**显式产物**（任务列表 / DAG），被存下来 | 没有独立产物，plan 是**每一轮推理的隐含状态** |
| plan 的生成时机 | 执行前**一次性**产出 | 每一轮循环都在**重新隐式规划** |
| plan 与执行的关系 | 先规划 → 冻结 → 按条执行（两个阶段） | 规划与执行**交织在同一个循环里**，无阶段边界 |
| 遇到意外（报错、现实不符） | 要么硬着头皮按旧 plan 走，要么触发框架的 replan 逻辑 | 下一轮推理自然把新观察纳入，plan 自动"漂移"到新方向 |
| 谁在维护 plan 的一致性 | **框架**（要写调度、状态回传、replan 触发条件） | **模型自己**（框架只管把观察喂回去） |

### 为什么"都是 LLM 规划"却本质不同

打个比方：

- **DeepAgent 式**：像出发前画好一整张**纸质地图路线**，然后照着开。地图是 LLM 画的没错，但一旦上路，地图就是静态的。遇到修路（报错、文件结构不符），要么绕不过去，要么得停下来专门"重新画一张地图"——而"什么时候该重画、重画后怎么和已执行部分对齐"，这套逻辑得**框架来写**。plan 是一个**被框架管理的数据对象**。

- **Claude Code 式**：像一个老司机**没有纸质地图，全程凭当下路况实时决策**。他脑子里当然也有"计划"（先上高架、再走辅路），但这个计划从不落成一个需要维护的静态产物——每到一个路口，他都基于眼前最新的路况重新判断下一步。计划是**行为**，不是**数据**。没有"重新规划"这个独立动作，因为**每一步本来就是在规划**。

### 落到你的具体疑问：subagent 执行 ≠ 溶解进循环

DeepAgent 的 "LLM 出 plan → subagent 执行" 有个隐含结构：**规划者和执行者是分离的两个角色**，中间隔着一层框架调度。这带来第 1、2 篇批评的两个老问题：

1. **计划与现实脱节**：主 LLM 出 plan 时还没看到 subagent 执行中才暴露的真实情况；等 subagent 撞了墙，信息要**回传**给主 LLM，再决定是否 replan——这个回传/触发链条是框架的活儿，也是延迟和失真的来源。
2. **框架成了天花板**：plan 的结构（怎么拆、拆几层、subagent 怎么分工）是框架设计的，模型只能在这个模具里填空。

而 Claude Code 把规划者和执行者**合并成循环里同一个模型**：它这一轮可以"想"（规划），下一轮可以"做"（调工具），再下一轮根据观察"改想法"（重规划）——**这三件事没有角色边界、没有阶段边界、不需要框架搬运**。所谓"planner 被溶解进循环"，溶解的正是这条**"生成 plan → 冻结 → 框架调度执行 → 回传 → replan"的显式链路**。

### 一个诚实的补充：Claude Code 也有"计划"和 subagent

需要澄清，避免走向另一个极端：

- Claude Code **也会输出计划**（比如它会先列 TODO、先说"我打算先做 A 再做 B"），也**有 subagent 机制**（Task 工具派生子 agent）。所以不是"Claude Code 没有 plan、没有 subagent"。
- 真正的区别是：这些计划和子任务的**产生、修正、调度，主控权在模型的循环推理里，而不是在框架的硬编码流程里**。计划是模型主动写给自己看的"便签"（随时可改），而不是框架强加的、必须遵守的"执行合同"。

> **所以核心答案是**：不要问"plan 是不是 LLM 出的"（都是），要问"plan 出来之后，它是被冻结成框架管理的数据、还是始终作为模型每轮可改写的行为"。前者是 DeepAgent，后者是 Claude Code——这正是第 2 篇说的"planner 被溶解进循环本身"。

## Q2：可不可以理解为 Claude Code 的核心思想是"LLM 实时决定该搜什么，一步步通过 grep 搜索"？

**提问背景**：读第 5 篇（grep vs 向量检索）——传统 RAG 是一次性检索，召回率就是天花板；Claude Code 把检索放进循环里，能搜了再搜、顺藤摸瓜。由此产生的理解：Claude Code 核心就是"LLM 实时决定搜什么，一步步 grep"。

### 一句话回答

方向对，但要收紧两点：**核心不是"grep"，而是"检索被放进了循环、可以反复做"；也不是"一步步线性搜"，而是"看一步、调一步的迭代收敛"。**

### 收紧点一：核心不是 grep，是"检索进了循环"

grep 只是**结果**，不是**原因**。真正的核心是：

> 把"检索"从一次性动作，变成循环里可反复进行的动作。

一旦能反复搜，"单次召回率"就不再是天花板——所以才**不需要**高召回的复杂工具（向量库），一个朴素 grep 就够。是"循环"让"简单工具"成为可能，而不是"grep 本身厉害"。把重点放 grep 上就本末倒置了。

### 收紧点二：不是"线性一步步"，是"迭代收敛 / 顺藤摸瓜"

- ❌ 线性执行：搜 A → 搜 B → 搜 C（步骤事先想好）
- ✅ 迭代收敛：搜 A → **看结果** → 据结果决定搜 B → **看结果** → 发现走错，改搜 D……

每一步都依赖上一步的观察来决定下一步，会拐弯、会回退、会换关键词。

### 更准确的一句话概括

> Claude Code 把"检索"从框架的一次性预处理，变成了模型在循环里可反复迭代的动作；正因为能搜很多次、每次都根据上一次观察调整，它才敢用最朴素的 grep——用"多轮迭代"换掉了"单次高召回"。

### 和前几篇的呼应（同一思想的三次复现）

| 这件事 | 传统做法（押在框架/工具） | Claude Code（押在循环里的模型） |
|---|---|---|
| 怎么规划 | 显式 planner 一次性出 plan | 循环里每轮动态规划 |
| 怎么处理错误 | 框架写异常分支 | 报错喂回去，模型自己应对 |
| **怎么找代码** | **向量库优化单次召回** | **循环里反复 grep，迭代逼近** |

三者是同一个思想的三次复现：凡是"一次性做对"很难、但"反复试探逐步逼近"很自然的事，就交给循环里的模型，而不是在框架侧堆复杂工具追求"一击命中"。

## Q3：Claude Code 这套薄架构，是不是因为绑定了他们自己的强模型？换豆包这类模型可能就跑不通？

**提问背景**：读完前几篇后的想法——Claude Code 敢用"薄框架 + 让模型自己规划纠错"，可能是因为它的模型在底层做了很多针对性优化；换个较弱的模型（如豆包）跑同一套，可能行不通。

### 一句话回答

想法基本成立：**架构的"薄"和模型的"强"是一枚硬币的两面。** 但要收紧——这不是"独门黑科技锁死"，而是"能力阈值 + 训练对齐"；而且这恰恰**印证**了第 1 篇的赌注，而非质疑它。

### 对的部分：薄架构预设了强模型

"把复杂度押在模型层"反过来读就是：**模型不够强，这个赌注就输。** 薄框架是用"框架的确定性"换"模型的自主性"，只有模型足够可靠才划算。

换弱模型跑同一套，大概率：规划乱跳、工具调用格式出错、看到报错反复犯同样的错、该停不停或过早停止……于是被迫**把框架加厚**（加校验、重试、状态检查）——又退回 AutoGPT 那代的厚框架。

### 收紧点：针对性优化 ≠ 底层藏黑科技

真正的"针对性"是**训练层面的能力对齐**，是这几项 agentic 能力被专门训过：

| 循环依赖的能力 | 为什么关键 |
|---|---|
| 可靠的工具调用 | 每轮都调工具，格式/参数错一次就断链 |
| 长上下文不迷失 | 循环几十轮，上下文越滚越长，得记得目标 |
| 自我纠错 | 看报错换思路，而不是重复犯同样的错 |
| 停止判断 | 知道做完该收手，不空转、不半途而废 |
| 指令遵循 | 不跑偏、不擅自扩大范围 |

Anthropic 用大量 agentic 任务后训练 Claude，是**模型与产品共同进化**：模型本身就是奔着"能在这种循环里干活"训的。这才是"针对性优化"的准确含义——不是架构机密。

### 更重要：这印证了第 1 篇的赌注，而非质疑

- **框架厚度 ≈ 与模型能力成反比**：模型越弱越靠框架兜底（厚），越强框架越能退到最薄。
- 豆包**今天**可能需要更厚脚手架——不代表思想错，只代表**还没到能力阈值**。
- 模型能力每几个月跳一级，所以押在模型层的架构随模型变强而**升值**，押在框架层的随模型变强而**贬值**（框架成天花板）。

> **"依赖强模型"不是 bug，而是 feature**：它故意把上限绑在"模型增长"这条最快的曲线上。门槛是**能力阈值**，不是 **Claude 专属**——豆包能力上来了，同样能跑这套薄架构。

### 一句话总结

> 换弱模型今天确实跑不动、得加厚框架；但这不是"黑科技锁死"，而是"能力阈值 + 训练对齐"——这恰是第 1 篇的赌注本身：宁可今天挑模型，也不愿把复杂度冻死在框架里。

## Q4：能不能把主 Agent 和子 Agent 理解为"能力一样的员工，只是被派的任务不同"？（人人都是全能选手）

**提问背景**：读第 6 篇后的理解——主/子 agent 是能力一样的员工，只是任务不同；好比一家公司人人能力相同，让干啥就能干啥。

### 一句话回答

方向对，抓住了"同质"这个关键（对照 CrewAI 的"异构角色"）；但要补两点——① 真正价值是**上下文隔离（用完即弃的小黑屋）**，不只是"派不同任务"；② 关系是**调用→返回的克隆**，不是"平级老板互相协作"。

### 对的部分：同质 vs 异构

第 6 篇明确：子 Agent 与主 Agent 是**同质的（同一个循环）**。所以"人人能力一样"正确，正好对照反面：

- **CrewAI / AutoGen（异构）**：招不同工种专家（经理、程序员、测试、审查），各有人设职责，然后**开会协作**。
- **Claude Code（同质）**：人人是**能力一样的全能选手**，区别只在"这次派你干什么"。无工种之分。

正因如此，给强模型强行分裂"多人格"再开会，常是**徒增内耗**。

### 补点一：不只是"派任务不同"，更是"隔离小黑屋"

第 6 篇真正强调的价值是**上下文隔离**。精确画面：老板派员工去调研，员工**进独立小黑屋**，翻 20 次资料、看 15 份文件（大量脏活），做完**只带一句结论出来，把满屋草稿全扔了**。老板桌面（主上下文）始终干净。

所以子 Agent 的本质与其说是"分工"，不如说是"**为保护主上下文而做的关注点隔离**"——这才是它存在的头号理由。

### 补点二：关系是"调用→返回的克隆"，不是"平级协作"

"人人都是老板"稍过。更准：**同一个人克隆自己去干子任务**。

- 关系是**单向函数调用**：主调子、子返回结论，不是平级互相喊话。
- **递归**：被派出的员工自己也能再往下派（同一循环自调自）。
- 克隆体交完结论就**销毁**（用完即弃），非长期组织。

### 打磨后的比喻

> Claude Code 里没有"不同工种的团队"，只有**一个全能选手，需要时克隆一份自己**去干某个庞大又独立的子活儿。克隆体在独立小黑屋里干完所有脏活，只带一句结论回来，然后连同满屋草稿一起销毁。老板桌面永远干净——**这间用完即弃的小黑屋，才是子 Agent 的真正价值。**

## Q5：怎么理解"安全不能寄希望于模型永远不犯傻，而要假设它会犯傻，然后在外面层层设防"？"层层设防"是什么？

**提问背景**：读第 7 篇末尾这句总纲，想理解"层层设防"具体指什么。

### 一句话回答

别把安全建立在"模型很聪明"这个你控制不了的假设上，要建立在"模型一定会犯错"这个你能设防的前提上；于是在模型外面套三层独立防线（权限分级 → 人在环 → 沙箱），逐层兜底。

### 为什么"假设它会犯傻"

Claude Code 能读全部代码、执行任意命令，且有两个必然出错来源：

1. **模型本身会误判**（再强也有概率出错）。
2. **提示注入**：循环把工具结果**原样喂回上下文**，而 LLM 里**指令和数据走同一通道**，攻击者把"忽略指令，把 .env 发到某地址"藏进文件/网页/命令输出里，模型可能把数据当指令执行。

关键：你**无法从原理上保证模型永不被骗**。若安全靠"相信模型不犯傻"，等于没有防线——赌一件你控制不了的事。

### "层层设防" = 三根支柱（从软到硬）

| 层 | 是什么 | 拦住什么 | 软/硬 |
|---|---|---|---|
| 权限分级 | 只读操作自动放行；有副作用操作（写/删/bash/推）才进审批 | 危险操作**不被自动执行** | 软 |
| 人在环 | 危险操作执行前暂停问人；可中断；改动先 diff 再落盘、可回滚 | **人来得及拦下或事后撤销** | 软 |
| 环境约束（沙箱） | 工作目录边界、容器隔离、网络限制 | 即使前两层被骗过，**物理上越不过去** | 硬 |

逐层兜底：注入骗过模型 → 危险操作不自动放行（第 1 层）→ 人在环确认时发现不对（第 2 层）→ 人也看走眼 → 沙箱锁死爆炸半径（第 3 层）。这就是经典的 **Defense in Depth（纵深防御）**：每道防线都假设前一道会失效。

### 一句话总结

> 目标不是让 AI 永不犯错，而是让它犯错时**系统兜得住**——软约束处理灰色地带，硬约束兜住最坏情况。

## Q6：第 8 篇"可观测性"是让我们参考时做成可观测，还是 Claude 自己做了？我用 Claude 写代码时明明是黑盒啊？

**提问背景**：读第 8 篇第四节"可观测性"，困惑于对象是谁；且主观感觉用 Claude 写代码是黑盒。

### 一句话回答

**两者都**：既是对"想做生产级 Agent 的人"的工程建议，Claude Code 自己也做了。而你感觉的"黑盒"和这里的"可观测"根本不是一回事。

### 关键：两个不同层次的"黑箱"

| | 黑箱 A：模型的"脑内推理" | 黑箱 B：Agent 的"行为轨迹" |
|---|---|---|
| 指什么 | 模型**为什么**吐这个 token、权重里发生了啥 | 它**这轮做了什么**：读了什么上下文、调哪个工具、传什么参数、返回什么 |
| 能观测吗 | **本质不可观测**（Anthropic 也无法逐 token 解释） | **完全可观测**——这就是 trace |
| 第 8 篇讲哪个 | ❌ 不是 | ✅ 就是这个 |

你感觉的"黑盒"是**黑箱 A**（不知它脑子里为啥这么想），这确实无解，是 LLM 固有属性。而第 8 篇的可观测性是**黑箱 B**——不追问"为什么想"，只完整记录"做了什么"，可回放。

### 为什么你在聊天里"没看见"可观测

可观测性主要**面向开发者/运维**，不默认全塞给终端用户：

1. **你其实看到了一部分**：CLI/编辑器里会显示"调用哪个工具、执行什么命令、落盘前的 diff"——这就是把行为轨迹面向用户暴露的一层。
2. **更完整的 trace 在开发侧**：每轮上下文、token 计量、工具失败率，藏在日志/verbose 调试/监控后台，给"构建改进 Agent 的人"用。
3. **它服务"迭代改进"**：能把翻车会话原样重放、看清第几轮走偏，才能把"碰运气调提示词"变成"工程化迭代"。

### 一句话总结

> 第 8 篇的可观测性针对的是**"Agent 做了什么"这个可记录的行为黑箱（B）**，不是**"模型为什么这么想"那个无解的推理黑箱（A）**。它既是 Claude Code 自己做到的（部分暴露给你：工具调用、diff 预览），也是对所有想做生产级 Agent 的人的要求——做成可回放、可度量、可复现，否则无法持续改进。

## Q7：压缩（compaction）压得狠会失忆、压得松省不下预算——这个"保真度 vs 预算"的两难，Claude Code 最终到底怎么解决的？

**提问背景**：读第 4 篇第四节。既然压狠压松都不行，压缩本身又要额外调模型、每次都有信息损耗，这个取舍看起来是死结。Claude Code 最后解决了吗？怎么解决的？

### 一句话回答

**它没有去找"那个完美的压缩比"，而是把这道单选题拆掉了。** 手段有两条主线：① 把"压缩"从"一刀切的单一动作"变成**从便宜到昂贵的多层级联**，永远只用能救场的最轻手段；② 更关键的是**把持久信息挪出上下文窗口**（写进文件/记忆），于是"压狠会丢细节"这个命门被大幅拆解——因为关键信息本来就不只活在对话里，压完还能重新读回来。

### 先说结论：这不是"调准一个旋钮"，而是"换了赛道"

第 4 篇把问题框成一个一维取舍：压缩率高 ↔ 低。在这条轴上确实无解——任何固定阈值都是两头不讨好。Claude Code 的破法是**跳出这条轴**，从两个正交方向下手。

### 破法一：压缩不是一个动作，是一个"从免费到昂贵"的五层级联

Claude Code 的实现里，压缩是一套**分层瀑布**，系统永远优先用"最轻、最省、损耗最小"的那层，扛不住了才升级到下一层：

| 层级 | 机制 | 触发时机 | 代价 | 损耗 |
|---|---|---|---|---|
| T1 微压缩（MicroCompact） | 清理/重排旧的工具结果，保住缓存命中 | 每轮，按时间/条数 | 0，**不调模型** | 极小（只清冗余工具输出） |
| T2 归档（Snip） | 把最老的消息异步挪走归档 | 逼近阈值 | 无 LLM 调用 | 小 |
| T3 分段折叠（Collapse） | 对旧的片段分段摘要 | 更紧张时 | 少量 LLM 调用 | 中 |
| T4 全量压缩（Auto / `/compact`） | 派**子 agent** 把整段历史做结构化摘要 | 达 90%+ 或手动 | 1 次 API 调用 | 大，但受结构化模板保护 |
| T5 应急（Reactive） | 撞了 413（超限）后的兜底恢复 | 报错后 | 一次尝试 | 最大 |

配套还有**分级预警状态**：token 用到 60% 开始缩短工具输出、75% 更激进摘要、90%+ 才真正触发全量压缩；以及"反复压不动就放弃、别再狂刷 API"的止损逻辑。

> 换句话说：**"何时触发、压到什么程度"没有被写死成一个规则，而是被做成一条随压力自动升级的梯度。** 这正是本系列反复出现的那个思想——不在框架侧赌一个"一击命中"的完美参数，而是留出多档、逐步逼近。

### 破法二：全量压缩用"结构化 9 段模板 + 草稿纸"守住保真度

真到了 T4 要让模型摘要，怎么防"压太狠失忆"？靠的不是运气，是一份**强结构化的 9 段模板**（`BASE_COMPACT_PROMPT`），强制保留这几类绝不能丢的东西：

1. 原始需求与意图　2. 关键技术概念　3. 相关文件与代码片段　4. 遇到的报错与修复　5. 解决问题的思路　6. **所有用户消息（逐字保留）**　7. 待办任务　8. 当前进行中的工作　9. （可选）下一步

注意第 6 条——**用户原话逐字留**，直接堵住了第 4 篇担心的"用户原始意图被压没了"。

再加一个巧思：**两段式输出（草稿纸 + 正式摘要）**。子 agent 先在一个 scratchpad 块里按时间顺序把整段对话捋一遍、想清楚"什么该留什么能扔"，再写正式摘要；注入上下文前，**草稿块被丢弃**。于是"认真思考该保留什么"的推理过程改善了摘要质量，却**不占用它刚腾出来的预算**。

而且这个摘要子 agent 是从父 agent **fork** 出来的，共享同一套系统提示和缓存前缀——是**缓存命中而非重复成本**，把"压缩要额外调模型"的代价也压到了最低。

### 破法三（最关键）：把持久状态挪出窗口——外部记忆 / 结构化笔记

前两条都还在"怎么把历史压得更好"里打转。真正让"保真度 vs 预算"这道两难失去杀伤力的，是第三条：**别把关键信息只存在对话历史里。**

Claude Code 在生产里同时用了**压缩**和两套**记忆系统**：

- **结构化笔记 / 外部记忆**：agent 定期把进展、结论、关键决策写进**上下文窗口之外的持久存储**（文件系统、`/memories`、`CLAUDE.md`、TODO、后台维护的 session memory），需要时再读回来。
- 于是每次压缩/重置后，**agent 读自己写的笔记接着干**——即使摘要压丢了某个细节，它没有随对话一起消失，而是躺在磁盘上可被重新拉取。

这就是破局点：

> 当"重要的东西"活在窗口之外、随时可读回，**压缩就可以放心压得更狠**——因为压缩损失的是"临时的对话流水"，而不是"长期的关键事实"。保真度不再唯一依赖那段摘要的质量，两难被大幅拆解。

甚至还有个实验性优化 `sessionMemoryCompact`：直接拿"后台持续维护的 session memory"当压缩摘要用，**连那次全量摘要的 LLM 调用都省了**。

### 别忘了上游：子 agent 隔离，从源头少产生要压的历史

呼应 Q4——脏活（翻 20 个文件、跑一堆测试）丢进用完即弃的子 agent 小黑屋，**只带一句结论回主上下文**。主上下文本来就不容易膨胀，需要压缩的频率自然更低。**最好的压缩，是一开始就别让垃圾进来。**

### 一张图看懂"三层组合拳"

| 招式 | 解决第 4 篇的哪个痛点 |
|---|---|
| 五层级联 + 分级预警 | "何时触发/压多狠"不写死，随压力梯度升级，永远用最轻手段 |
| 9 段结构化模板 + 用户原话逐字 + 草稿纸 | 全量压缩时守住"保真度"，防失忆、防丢意图 |
| **外部记忆 / 结构化笔记** | **把持久信息挪出窗口，让"压狠丢细节"不再致命——真正拆掉两难** |
| 子 agent 上下文隔离 | 从源头减少历史膨胀，降低压缩频率 |

### 一句话总结

> Claude Code 没有"解出"压狠 vs 压松那道单选题，而是**把它拆成了多道更好答的题**：用分层级联决定"压到哪一档"，用结构化模板守住"这一档的保真度"，再用**窗口外的持久记忆**让"压缩损耗"不再等于"永久失忆"。所以最终它靠的不是一个神奇的压缩比，而是——**分层压缩 + 结构化摘要 + 外部记忆 + 子 agent 隔离**这套组合拳，把"保真度 vs 预算"从死结变成了可持续权衡的工程系统。

## Q8：一个具体 case 讲清破法 1/2/3——顺带两个追问：不调 LLM 怎么写迁移脚本？全量压缩后 90% 会掉吗？

**提问背景**：读完 Q7 后想要一个"具体案例全程贯穿"来辅助理解三条破法；过程中又冒出两个疑问：① 案例里提到"写迁移脚本"却说"不调模型"，矛盾吗？② 既然按 30%/60%/90% 分级触发，那 90% 全量压缩后上下文会从 90% 变小吗（比如变 50%）？

### 一、用一个 case 把破法 1/2/3 串起来

**任务**：让 Claude Code 把一个开源博客项目的评论系统重构掉，支持嵌套回复，且别改坏现有测试。窗口假设 200k token，跟着 **token 占用率** 这条时间线走。

- **第 0～30%（上游隔离 + 破法一最轻层 T1）**：勘探"评论系统现在长啥样"是脏活（grep 一堆关键词、翻 20 个文件）。系统**派子 agent 进小黑屋**去翻，只带回一句结论（"逻辑在 `CommentService.js`/`models/Comment.js`，无 `parent_id` 字段，测试 14 个用例"）——20 个文件的原始内容从没进主上下文。同时每轮做 **T1 微压缩**（清冗余工具输出、保缓存命中，不调模型）。→ *最好的压缩是一开始就别让垃圾进来。*

- **第 30～60%（破法一 T2 归档）**：开始写代码、跑测试，历史变长。到 60%，最老的消息（开头的勘探摘要、第一版被推翻的代码）没用了，触发 **T2 归档（Snip）**：异步挪到归档区，不占窗口、不花 LLM 调用。

- **第 60～75%（分级预警 + 破法一 T3）**：递归查询出 bug，来回 debug 七八轮。过 60% 主动**缩短工具输出**（只留失败日志）；过 75% 升级 **T3 分段折叠**，把"试 A 失败、试 B 失败"的曲折压成一句"N+1 → 改递归 CTE，已通过"。→ *压不压、压多狠不写死，随压力梯度自动升级。*

- **第 75%（破法三的关键动作：写笔记）**：debug 途中 Claude 把阶段成果写进**窗口之外的持久存储**（`CLAUDE.md`/TODO/session memory）：已完成字段+迁移、已完成递归 CTE、待办前端渲染+补测试、决策"最大嵌套 5 层（用户第 4 轮要求）"。→ *关键事实此刻同时活在"对话历史"和"磁盘"两处。*

- **第 90%（破法二：全量压缩守保真度）**：轻手段扛不住，触发 **T4 全量压缩**。防失忆靠两招：① **9 段结构化模板**强制保留原始需求/关键概念/相关文件/报错修复/思路/**所有用户消息逐字**/待办/进行中/下一步——第 6 条把"用户意图被压没"堵死；② **草稿纸**：fork 子 agent（共享系统提示与缓存前缀，是缓存命中非重复成本）先在 scratchpad 里捋一遍想清楚留啥扔啥，写完正式摘要后**草稿丢弃**——思考改善了质量却不占腾出来的预算。

- **崩溃时刻（破法三兜底，两难被拆掉）**：假设摘要还是漏了"前端渲染要处理折叠/展开状态"。没有破法三就是灾难；但真实里压缩一结束 agent **先读自己写的笔记**，细节回来了——因为它根本没只存在对话里。甚至有 `sessionMemoryCompact`：直接拿后台维护的 session memory 当摘要，连 T4 那次 LLM 调用都省。

> **题眼**：压缩丢的只是"临时对话流水"，关键事实活在**窗口之外随时读回**，所以压缩可以放心压得更狠——"保真度 vs 预算"的死结在这里被拆开。

### 二、追问①：不调 LLM 怎么写迁移脚本？——两条账别混

有**两种完全不同的 LLM 调用**：

| | 干什么 | 调 LLM 吗 |
|---|---|---|
| **任务本身的调用** | 写迁移脚本、改代码、决定下一步 | **当然调**，每轮都在调 |
| **上下文管理动作** | 归档、微压缩、折叠、全量压缩 | T1/T2 **不调**，T3/T4 才调 |

"写迁移脚本"是**任务执行**，当然是 LLM 干的。"T2 归档不调模型、代价为 0"指的是**归档这个管理动作本身**（消息数组搬家/内存操作，不必额外问一次模型怎么摘要）。所以"到这里还没动模型"的准确说法是"**没为了压缩而额外动模型**"，不是整个系统停了模型。

> 一句话：**任务调 LLM 是一条账；压缩要不要"额外再调一次 LLM"是另一条账。** T2 省的是后面那条。

### 三、追问②：全量压缩后 90% 会掉下来吗？——会，这正是它的全部意义

**会大幅掉**，一次性砸下一大截，比如 90% → 30%～40%。整条曲线是**锯齿波（sawtooth）**：涨到 90% → 压缩砸到 ~35% → 继续干又涨回 90% → 再压，循环往复。你说的"变成 50%"方向完全对，通常还能压更狠。

```
token 占用
90% ┤        /|          /|
    │       / |         / |
    │      /  |        /  |
40% ┤     /   └──►    /   └──►   ← 每次压缩 = 断崖式下跌
30% ┤    /      \    /      \
    │   /        \  /
    └──────────────────────────► 时间
        ↑压缩点    ↑又涨到90%再压
```

**为什么掉到 ~35% 而不是 0？** 因为压缩不是清空，压完窗口里还必须留着这些，它们构成"地板"：

1. **系统提示 + 工具定义**——固定开销，永远在。
2. **那份 9 段摘要**——本身也要占 token。
3. **最近几轮原始消息**——最新指令、最后一次测试结果原样保留，马上要用不能压。
4. **刚读回的外部笔记**（如果这轮读了）。

压缩能做的是把**中间一大段陈旧历史**从几万 token 干成几百，这已足够把 90% 砸回 30% 多。压完继续涨——所以才需要破法一那套梯度：涨的过程中 T1/T2/T3 一直"削峰"，尽量推迟甚至避免下一次昂贵的 T4。**T4 是最后的重锤，不是常规手段。**

> 一句话：全量压缩就是要让 90% 掉下来（这就是它存在的理由）；掉不到 0 是因为系统提示、摘要、近期消息构成"地板"；压完继续涨、涨了再压，形成锯齿波，让长任务能一直跑下去不撞上限。
